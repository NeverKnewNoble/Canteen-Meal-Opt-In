# Canteen meal opt-in — database schema & PostgreSQL (CSV-friendly)

This document describes the **application database** and gives **PostgreSQL DDL** designed so you can **`\copy` Supabase-style CSV exports** including **`id`** columns (numeric ids). It matches the app’s behaviour in `src/types` and `src/utils/*`.

**Why bigint instead of uuid?** Supabase exports often use **integer / bigint** primary keys. Importing into `uuid` columns fails (`invalid input syntax for type uuid: "13"`). Using **`bigint`** for all ids and foreign keys lets you import **`id`, `department`, `menu_id`, etc.** directly from CSV without staging maps.

**App note:** The Next.js app historically assumed UUID-shaped strings; with **`bigint`**, Node’s `pg` driver typically returns ids as **strings** (e.g. `"13"`) for large integers, which usually still works with the existing API. If anything breaks, align `src/lib/db/repos.ts` and types with **`string | number`** ids. Validate after cutover.

**Auto-ids:** Primary keys use **`GENERATED BY DEFAULT AS IDENTITY`**. API `INSERT`s omit `id` and Postgres assigns the next value. CSV import can still **supply explicit `id`** values (`BY DEFAULT` allows overrides). If you created tables from older DDL without identity, run `docs/migrations/001-bigint-identity-for-app-inserts.sql` once.

| Table | Purpose |
|-------|---------|

| `users` | Staff members; `department` is **`departments.id`** (bigint), not the display name. |

| Column | Type | Notes |

## Part 2 — Create database (bigint, import-friendly)

### Dependency order

```text
departments
    ↑
  users
    ↑
selections ← meals → menu
                ↑________|
           (todays_special)
```

`menu.todays_special` references `meals.id`, while `meals.menu_id` references `menu.id`. Create **`menu`** first with **`todays_special` unconstrained**, create **`meals`**, then add the FK from **`menu.todays_special`** → **`meals`**.

### Canonical DDL (matches `src/lib/db/repos.ts`)

Use **`docs/migrations/000-initial-schema.sql`** as the single source of truth for a new database. It creates **bigint identity** primary keys, **`menu.status` as `text`** with a CHECK constraint (not a Postgres enum), indexes, foreign keys, and the **`selections.updated_at`** trigger.

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f docs/migrations/000-initial-schema.sql
```

Then import CSV in **FK order** (Part 3). You do **not** need `001-bigint-identity-for-app-inserts.sql` on a fresh install from `000`.

### Optional: at most one selection per user per meal

```sql
ALTER TABLE public.selections ADD CONSTRAINT selections_user_meal_unique UNIQUE (user_id, meal_id);
```

### Already created tables without identity?

If `INSERT` from the app fails with **`null value in column "id"`**, your tables use plain `bigint` PKs. Run **`docs/migrations/001-bigint-identity-for-app-inserts.sql`** (psql, GUI, or migration runner). The script is **idempotent**—it skips tables whose `id` is already an identity column.

The **`updated_at`** trigger is already included in **`000-initial-schema.sql`**.

## Part 3 — Importing CSV (`\copy` including `id`)

### Rules

1. **Column list** in `\copy` must match your CSV **header order** exactly.
2. Import in **FK order** (below).
3. If **`menu.todays_special`** in the CSV points at meals that are **not loaded yet**, either:
   - export/import **`menu`** with **`todays_special` empty / NULL**, then after **`meals`** run  
     `UPDATE public.menu SET todays_special = …` from a staging file, or  
   - import **`menu`** (with NULL `todays_special`) → **`meals`** → second CSV or SQL to set specials.

### Suggested import order

| Step | Table | Depends on |
|------|--------|------------|
| 1 | `departments` | — |
| 2 | `menu` | (optional: NULL `todays_special` first) |
| 3 | `meals` | `menu` |
| 4 | `users` | `departments` |
| 5 | `selections` | `users`, `meals` |
| 6 | Patch `menu.todays_special` | `meals` |

### CSV column order vs `\copy` (important)

`WITH (HEADER, …)` **skips the header row** but Postgres does **not** map header names to table columns. Fields are read **left to right**: field 1 → first name in your `\copy` list, field 2 → second, etc.

**Supabase exports** often order columns like the table definition, e.g. `id, name, date, deadline, status, created_at, todays_special` — so **`created_at` comes before `todays_special`**. If you use `(…, todays_special, created_at)`, the **timestamp lands in `todays_special`** and you get:

`invalid input syntax for type bigint: "2026-01-26 …"`

**Fix:** Open the CSV’s **first line** (headers) and set your `\copy` column list to the **same order** as the data columns (excluding columns you drop by using a staging table).

**Do not use this order** (it puts the **timestamp** into `todays_special` when the CSV has `created_at` before `todays_special`):

```sql
-- WRONG — leads to: invalid input syntax for type bigint: "2026-01-26 …"
\copy public.menu(id, name, date, deadline, status, todays_special, created_at) FROM '...' WITH (...);
```

**Use this order** for typical Supabase `menu` CSVs (`…, status, created_at, todays_special`):

```sql
\copy public.menu(id, name, date, deadline, status, created_at, todays_special) FROM '/path/to/menu_rows.csv' WITH (FORMAT csv, HEADER, QUOTE '"', ESCAPE '''', FORCE_NULL (todays_special));
```

If the export includes **`updated_at`** (or other columns), either add them to the `\copy` list in that position (and add matching columns to the table) or **remove those columns from the CSV** before import.

### Example `\copy` commands (adjust paths and column lists to your files)

Run in **psql** connected to your database. Use your real CSV paths.

```sql
\copy public.departments(id, name, created_at) FROM '/path/to/departments_rows.csv' WITH (FORMAT csv, HEADER, QUOTE '"', ESCAPE '''');

-- Menu: match column ORDER to your CSV header row (Supabase often has created_at before todays_special):
\copy public.menu(id, name, date, deadline, status, created_at, todays_special) FROM '/path/to/menu_rows.csv' WITH (FORMAT csv, HEADER, QUOTE '"', ESCAPE '''');

-- Meals: Supabase CSV often has empty description → COPY sends NULL. You MUST relax NOT NULL, import, fix, restore:
ALTER TABLE public.meals ALTER COLUMN description DROP NOT NULL;
\copy public.meals(id, name, description, menu_id, created_at) FROM '/path/to/meals_rows.csv' WITH (FORMAT csv, HEADER, QUOTE '"', ESCAPE '''');
UPDATE public.meals SET description = '' WHERE description IS NULL;
ALTER TABLE public.meals ALTER COLUMN description SET NOT NULL;

\copy public.users(id, name, department, created_at) FROM '/path/to/users_rows.csv' WITH (FORMAT csv, HEADER, QUOTE '"', ESCAPE '''');

\copy public.selections(id, user_id, meal_id, opted_in, created_at, updated_at) FROM '/path/to/selections_rows.csv' WITH (FORMAT csv, HEADER, QUOTE '"', ESCAPE '''');
```

### Common errors

| Error | Cause |
|--------|--------|
| `extra data after last expected column` | `\copy` column list has fewer columns than fields **per row** in the file (e.g. file still has `id` but list does not, or the opposite). |
| `invalid input syntax for type uuid` | Table still uses `uuid`; use this doc’s **bigint** DDL or remove uuid columns. |
| `invalid input syntax for type bigint` / FK violation | Wrong import order, or orphaned `department` / `menu_id` / `user_id` / `meal_id`. |
| `invalid input syntax for type bigint: "2026-…"` on `todays_special` | **Column order mismatch:** a **timestamp** is in the slot mapped to `todays_special`. Reorder `\copy` to match the CSV (often `created_at` before `todays_special`). See subsection above. |
| `null value in column "description" … violates not-null constraint` (`meals`) | Empty CSV cells become **NULL**. `meals.description` is `NOT NULL`. **Option A:** `ALTER TABLE public.meals ALTER COLUMN description DROP NOT NULL;` → `\copy` → `UPDATE public.meals SET description = '' WHERE description IS NULL;` → `ALTER COLUMN description SET NOT NULL;`. **Option B:** Put `""` or text in empty description cells in the CSV. |
| Boolean / timestamp | Use `t`/`f` or `true`/`false` per Postgres CSV rules; timestamps in ISO format. If needed, `\copy` into a **staging** table with `text` columns, then `INSERT ... SELECT col::bigint`, `col::timestamptz`, etc. |

### Dropping old tables (start over)

Respect FK order (children first):

```sql
DROP TABLE IF EXISTS public.selections CASCADE;
DROP TABLE IF EXISTS public.users CASCADE;
DROP TABLE IF EXISTS public.meals CASCADE;
DROP TABLE IF EXISTS public.menu CASCADE;
DROP TABLE IF EXISTS public.departments CASCADE;
```

Then rerun **`docs/migrations/000-initial-schema.sql`**.
